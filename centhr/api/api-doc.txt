CENTHR API - DOCUMENTATION
==========================

One-way sync of HR records from this site to remote Frappe/HRMS sites
("targets") through the target's REST API (/api/resource/<DocType>).
Flow: doc event (hooks.py) -> enqueue_* -> background job -> HTTP request
-> one CentHR API Logger record per request.


1. HOOKS (centhr/hooks.py)
--------------------------
  Employee           after_insert -> post   | on_update -> update | on_trash -> delete
  Leave Application  on_submit    -> post   | on_cancel -> cancel | on_trash -> delete
  Attendance         on_submit    -> post   | on_cancel -> cancel | on_trash -> delete
  Leave Allocation   after_insert -> post   | on_update, on_cancel, on_update_after_submit -> update
                     | on_trash -> delete
  Employee Checkin   after_insert -> post   | on_update -> update | on_trash -> delete
  Shift Type         after_insert -> post   | on_update -> update | on_trash -> delete
  Salary Component   after_insert -> post   | on_update -> update | on_trash -> delete
  Salary Structure, Salary Structure Assignment, Additional Salary,
  Payroll Entry      after_insert -> post   | on_update, on_cancel, on_update_after_submit
                     -> update | on_trash -> delete

  The payroll doctypes are built like Employee (one self-contained file
  per action, no common/ code). See section 10.

  Leave Allocation, Employee Checkin and Shift Type use the shared code in
  centhr/api/common/. See section 8.

  update/attendance.py and update/leave_application.py exist but are NOT
  in hooks.py, so they do not run.
  after_install/after_migrate add Employee custom fields territory,
  cost_center and channel (customization/employee.py).


2. COMMON PATTERN (all files)
-----------------------------
  - Targets:  rows of CentHr Settings > authorization where company =
              doc.company. No row = nothing is queued.
  - Job:      queue "short", job_id "centhr_<doctype>_<action>::<name>",
              deduplicate, enqueue_after_commit. A failure on the target
              never blocks or rolls back the local save.
  - Auth:     "Authorization: token <api_key>:<api_secret>".
  - Employee: matched on the target by employee_number (or the name, if
              it is empty). Not found = Failed log "Employee X is not
              synced to the target system".
  - Payload:  all value fields of the DocType meta, child tables too.
              None becomes "".
  - HTTP:     timeout (10, 30) s, 2 retries.
  - Errors:   401/403 key/secret, 404 base URL, 409 already exists,
              400/417/422 rejected, 5xx server error. HTML error pages
              are reduced to title + traceback lines.
  - Log:      insert_log writes every request (Success or Failed) with
              method, endpoint, status, payload, response (10000 chars)
              and target_reference.
  - Failure:  CentHRSyncError or any exception is logged, the next target
              is tried, then notify_failure alerts the users in
              CentHr Settings > error_alerts.


3. POST - centhr/api/post/
--------------------------
employee.py - sync_employee(employee)
  Creates the Employee on the target after insert. Stops if the
  employee_number already exists on the target. Checks the required
  fields (department, company_email, territory, cost_center, channel). If
  one is empty, it logs Failed and does not send. Otherwise it sends POST.
  409 = Success. Sync the Employee first: all other files depend on it.

leave_application.py - sync_leave_application(leave_application)
  Creates a submitted Leave Application (docstatus 1) on submit. Clears
  salary_slip and amended_from. Stops if a non-cancelled record with the
  same employee, leave_type, from_date and to_date exists. Otherwise it
  sends POST.

attendance.py - sync_attendance(attendance)
  Same as leave_application, for Attendance. Clears leave_application,
  attendance_request and amended_from. The duplicate check is a
  non-cancelled record with the same employee + attendance_date.


4. UPDATE - centhr/api/update/
------------------------------
employee.py - update_employee(employee, employee_number)
  Runs on every save except insert. Finds the target Employee by the OLD
  employee_number (from before the save), so a renamed number still
  matches. Sends PUT with all fields except lft, rgt and old_parent
  (the target calculates these).

leave_application.py - update_leave_application(leave_application, lookup)
  Drafts only (docstatus 0). Finds the target draft by the OLD employee,
  leave_type, from_date and to_date, then sends PUT. No draft = Failed
  log. Not hooked.

attendance.py - update_attendance(attendance, employee, attendance_date)
  Drafts only. Finds the target draft by the OLD employee +
  attendance_date, then sends PUT. No draft = Failed log. Not hooked.


5. DELETE / CANCEL - centhr/api/delete/
---------------------------------------
The local doc may be gone, so the job gets a snapshot dict of the
needed fields, not a document name.

employee.py - delete_employee(employee, employee_name, employee_number, company)
  Sends DELETE for the target Employee. Not found = Success. If the
  delete fails with LinkExistsError, it gets the linked records
  (linked_with.get). Employees with reports_to = this employee are
  unlinked. All other linked records are cancelled (if submitted) and
  deleted. Then it sends DELETE again.

leave_application.py - sync_leave_application_removal(action, snapshot)
attendance.py        - sync_attendance_removal(action, snapshot)
  action = "cancel" or "delete". The job finds the target record
  (same keys as in post) with this docstatus:
    cancel -> [1] | delete draft -> [0] | delete cancelled -> [1, 2]
  Submitted match -> PUT docstatus 2. If action is delete -> DELETE.
  No match = Success.


6. CENTHR API LOGGER - centhr/centhr/doctype/centhr_api_logger/
---------------------------------------------------------------
centhr_api_logger.py
  - before_insert: stores the job (sync_method + sync_kwargs) that wrote
    the log, and moves the raw error to error_details.
  - resync(): only for a Failed log that is not resynced, max 3 attempts.
    Queues the same job again. For old logs, it works out the job from
    request_method + docstatus. mark_resynced() marks all failed logs of
    that job, so one click is enough.
  - resync_logs(names): bulk resync from the list view.
  - run_resync(log): the background job. A resynced log gets
    resynced_from and resync_count + 1.

readable_error.py - get_readable_error(log)
  Changes the raw error into a short message the user can act on
  (connection, HTTP status, missing fields, employee not synced,
  target validation message).

centhr_api_logger.js / centhr_api_logger_list.js
  "Resync" button on the form, or the reason why resync is not possible.
  "Resync" action in the list view.

7. DATA MIGRATION - centhr/api/migrate/
---------------------------------------
  Pull direction: copies records FROM the company's CentHR site (the
  CentHr Settings row of that company) INTO this site. Used by the
  desk tool "Centhr Data Migration Tool" (/app/centhr-data-migration-tool).

  Sections, in the order to migrate them:
    Leave Type -> Employee -> Leave Policy Assignment / Leave Allocation
    -> Leave Application -> Attendance

  client.py - TargetClient(company)
    GET /api/resource with pagination (500 per page). Same timeout,
    retries and HTTP error messages as the push files. A failure raises
    MigrationError with the request details for the log.

  employee_map.py - EmployeeMap
    Matches employees on employee_number (or the name when it is empty),
    the same key as the push sync.

  base.py - Migrator
    fetch(filters): reads the records, then sets migration_status per row:
      Already Exists  a matching record is on this site
      Success         this tool created the matching record
      Failed          the last attempt failed (error + log link)
      Pending         never tried
    migrate(name): reads the full record, stops if it already exists here,
      maps Employee links, clears optional links that do not exist here,
      drops attachments and naming fields, inserts, and submits it when it
      is submitted on the CentHR site. Each record writes one CentHR API
      Logger entry (reference_name = CentHR name, target_reference = name
      here) with sync_method <module>.migrate, so Resync retries that one
      record. Cancelled records are not fetched.

  employee.py, leave_type.py, leave_policy_assignment.py,
  leave_allocation.py, leave_application.py, attendance.py
    Per-DocType columns, filters and duplicate key.

  While a record is migrated, frappe.flags.centhr_migration is set. The
  push hooks (post/employee, update/employee, post/leave_application,
  post/attendance, and all Leave Allocation, Employee Checkin and Shift
  Type hooks) check it, so migrated records are not sent back.

  Tool endpoints (centhr_data_migration_tool.py):
    get_records(section, company, filters)  - fetch, synchronous
    migrate_records(section, company, names) - queues run_migration on
      the long queue; progress per record over realtime event
      "centhr_migration_progress".


8. LEAVE ALLOCATION, EMPLOYEE CHECKIN, SHIFT TYPE - centhr/api/common/
-----------------------------------------------------------------------
  The post/, update/ and delete/ files of these doctypes only hold the
  hook and the job. They call the shared code in common/:

  record_sync.py
    enqueue_job(method, doc, **kwargs)
      Queues the job on "short" after commit. Skips records written by the
      migration tool, and companies with no CentHr Settings row.
    sync_record(doctype, name) - used by post and update
      Finds the record on the target. Not found = POST. Found = PUT. So an
      update also creates a record that failed to POST before.
      Target record submitted: PUT only "Allow on Submit" fields, or
      docstatus 2 when the local record is cancelled.
    delete_record(doctype, name, company, label) - used by delete
      Not found = nothing to do. Target record submitted = PUT docstatus 2
      first. Then DELETE. 404 = Success.
    One Redis lock per record, so two jobs of one record do not run at
    the same time (for example insert and submit).

  Target name of a record:
    - Shift Type: the same name on both sites.
    - Others: target_reference of the successful POST log. For a record
      that the migration tool copied from CentHR: reference_name of its
      migration log (sync_method starts with "centhr.api.migrate.").
  Target Employee: employee_number = local employee_number (or the local
    name). If no match: name = that value with an empty employee_number,
    for employees that the migration tool copied from CentHR.
  Payload: all value fields, docstatus for submittable doctypes. Links to
    local records that are not synced are not sent:
      Leave Allocation  compensatory_request, leave_period, leave_policy,
                        leave_policy_assignment
      Employee Checkin  attendance
  Shift Type has no company, so it goes to every target once.
  Employee Checkin uses the company of its employee.

  target_client.py - TargetClient(target, ref)
    get_list, insert, update, delete on /api/resource. Writes one
    CentHR API Logger record per request.


9. WEB FORM EMAIL OTP - centhr/api/otp/web_form.py
--------------------------------------------------
  The Attendance (Employee Checkin) and Leave Application web forms ask
  for a code that is sent to the employee's company email before they
  save.

  public/js/web_form_otp.js (webform_include_js for both doctypes)
    Submit -> send_otp -> dialog "Verify Your Email" -> verify_otp ->
    the form saves with the token. "Resend Code" sends a new code.

  send_otp(employee) - guest
    6-digit code to Employee.company_email (Active employees only).
    Only a hash is kept in Redis, for 10 minutes. Max 5 codes per
    employee in 10 minutes.
  verify_otp(employee, otp) - guest
    5 wrong codes cancel the code. A correct code returns a token for
    this employee, valid for 10 minutes.
  validate_web_form_otp - before_insert, web form submissions only
    No valid token for the same employee = the record is not saved.
    The token is deleted after commit, so a failed save can be fixed
    and sent again without a new code.
  Needs an outgoing Email Account.


10. PAYROLL - centhr/api/post|update|delete/<doctype>.py
--------------------------------------------------------
  Salary Component, Salary Structure, Salary Structure Assignment,
  Additional Salary and Payroll Entry. Same pattern as Employee
  (section 2): CentHr Settings row of doc.company, token auth, "short"
  queue after commit, one log per request, alert on failure. Resync
  works from the log (sync_method / sync_kwargs).

  Target endpoints:
    GET    /api/resource/<DocType>?filters=...   find the record
    POST   /api/resource/<DocType>               create
    PUT    /api/resource/<DocType>/<name>        update, submit, cancel
    DELETE /api/resource/<DocType>/<name>        delete

  Record on the target found by:
    Salary Component             name (no company: every target once)
    Salary Structure             name (set by the user)
    Salary Structure Assignment  employee + salary_structure + from_date
    Additional Salary            employee + salary_component + amount +
                                 payroll_date (from_date if recurring)
    Payroll Entry                company + payroll_frequency + start_date
                                 + end_date + posting_date
  Employee: target employee with the same employee_number (or the local
  name). Payroll Entry maps every row of its employees table.
  Update jobs get the key values from before the save, so a changed draft
  is still found.

  post   Found = Success "already exists", nothing sent. Else POST with
         the local docstatus.
  update Not found = POST (cancelled locally = nothing to do).
         Target draft = PUT all fields (docstatus 1 submits it there).
         Target submitted = PUT docstatus 2 when cancelled locally, else
         only "Allow on Submit" fields.
  delete Not found = Success. Target submitted = PUT docstatus 2 first,
         then DELETE. A submitted target record that belongs to a local
         amendment is not touched.

  Checked first, else Failed "... Sync it first":
    Salary Structure    every salary component exists on the target
    Salary Structure Assignment  structure is submitted on the target
    Additional Salary   salary component exists on the target

  Not sent (local-only links, or set by the target):
    Salary Component    accounts
    Salary Structure    letter_head, mode_of_payment, payment_account,
                        additional_salary in earning/deduction rows
    Salary Structure Assignment  amended_from, payroll_payable_account,
                        payroll_cost_centers
    Additional Salary   amended_from, ref_doctype, ref_docname
    Payroll Entry       amended_from, branch, department, designation,
                        grade, project, bank_account, status,
                        salary_slips_created, salary_slips_submitted,
                        error_message; department/designation of rows

  Payroll Entry: the sync only submits it on the target when it was
  submitted here. The target's own on_submit then creates DRAFT Salary
  Slips. Salary Slips are never submitted by the sync. The target's own
  cancel removes them.
